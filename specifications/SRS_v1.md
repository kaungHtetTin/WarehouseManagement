# Warehouse Management System (SaaS)

## Software Requirements Specification (SRS) v1

## 1) Document Control
- **Project**: Multi-tenant Warehouse Management System
- **Version**: v1.0 (Draft for review)
- **Language**: UI supports Myanmar + English
- **Scope**: Requirements and behavior definition only (no implementation)

## 2) Product Vision
Build a public SaaS platform where multiple warehouse businesses (tenants) use one system.  
Each tenant has one `Super Admin` with full control over that tenant's data, users, branches, permissions, and operations.

## 3) Goals and Objectives
- Centralize warehouse, inventory, shipment, and voucher operations.
- Support one truck trip delivering to multiple destinations/stops.
- Track freight payment status per item/line and voucher.
- Provide role/permission-based access within each tenant.
- Support responsive UI on mobile/tablet/laptop/desktop.
- Allow printing only from computer/desktop.
- Let each tenant publish one public portfolio page to promote business.
- Support monthly subscription plans for tenant app usage.

## 4) Business Model and Tenancy
- The system is **multi-tenant**.
- Each warehouse service company is a separate tenant (`organizations`).
- Tenant data is strictly isolated by `organization_id`.
- One tenant can own multiple warehouses/branches.
- One tenant's users cannot access another tenant's records.
- Each tenant can have one public-facing profile page under the platform.

## 5) User Types and Role Model
- **Platform Admin** (internal/system owner): manages tenant onboarding and global settings.
- **Tenant Super Admin**: full control within one tenant; can create users, roles, permissions.
- **Tenant Manager**: warehouse and shipment operational control per granted permissions.
- **Tenant Clerk/Operator**: creates vouchers, manages intake/loading/delivery updates as allowed.
- **Viewer/Finance roles**: optional, read-only or payment-focused based on permission assignment.

Permissions are RBAC-based with optional warehouse-level scoping.

## 6) Functional Scope

### 6.1 Authentication and User Management
- Secure login/logout.
- Password reset/change.
- Create/edit/deactivate users.
- Assign role(s) and permission(s) by tenant Super Admin.
- Optional per-warehouse user assignment.

### 6.2 Role and Permission Management
- Tenant Super Admin can:
  - Create roles.
  - Assign permissions to roles.
  - Directly assign/revoke permissions for users (optional override).
- Permission checks apply to all actions, including payment operations.

### 6.3 Warehouse Management
- Create/edit/deactivate warehouse branches.
- Configure branch code, city, address, contact, status.
- View real-time branch-level inventory balances.
- Restrict visibility by role/warehouse access.

### 6.4 Inventory Management
- Category-based product/item organization.
- Maintain product master data (name, unit, weight/volume optional).
- Track stock by warehouse and item.
- Auto stock movement records generated by voucher lifecycle events.

### 6.5 Vehicle Management
- Create/edit/deactivate vehicles and capacity metadata.
- Assign vehicles to shipment trips.
- Track trip status progression.

### 6.6 Voucher and Shipment Operations
- Use one main operational voucher type for merchant intake/shipment.
- Use a separate printable **Driver List / Manifest**.
- Workflow:
  1. Merchant deposits goods at source warehouse.
  2. Operator registers items and creates voucher.
  3. Items are planned/loaded to a trip.
  4. Driver receives printed list/manifest.
  5. Trip delivers to one or more stops/destination warehouses.
  6. Destination confirms receipt.
- Support partial loading and partial delivery due to truck capacity limits.

### 6.7 Freight Payment Tracking
- Payment tracking is permission-based.
- Suggested statuses:
  - `UNPAID`
  - `PARTIAL`
  - `PAID`
  - `WAIVED` (optional)
- Track who updated status, when, and amount details.

### 6.8 Printing
- Printable documents:
  - Merchant Voucher/Receipt
  - Driver Manifest/List
- Printing supported only on desktop/computer environment.

### 6.9 Audit and Traceability
- Audit key events:
  - User/role changes
  - Voucher creation and status transitions
  - Payment status updates
  - Stock-impacting operations
- Store actor, timestamp, entity, action, before/after data (where feasible).

### 6.10 Organization Public Portfolio Page
- Each tenant can create and maintain one public page/profile.
- Public page supports:
  - Business name and tagline
  - Description/About
  - Services list
  - Contact phone/email
  - Main address/city
  - Logo and cover image
  - Optional gallery and social links
- Public page can be published/unpublished by tenant Super Admin (or delegated role).
- Public page route should be unique (slug/subdomain-style identifier, final format to be chosen).
- Public page content is public-read; edit access is permission-controlled inside tenant admin.

### 6.11 Subscription and Billing Management
- The platform offers monthly subscription plans.
- A tenant must have an active subscription to use protected app features (policy configurable, e.g. grace period).
- Subscription includes:
  - Plan name
  - Monthly price
  - User/warehouse limits (optional by plan)
  - Feature flags (optional by plan)
- Billing lifecycle:
  - Trial (optional) -> Active -> Past Due -> Suspended -> Cancelled/Expired
- Record invoice/billing history and subscription payment transactions.
- Access to subscription and billing pages is permission-based (platform admin + authorized tenant roles).

## 7) Business Rules
- One trip may contain goods for multiple destinations.
- One trip may carry only a subset of source warehouse pending goods.
- Destination warehouse can view incoming trip and expected items.
- Stock movement should remain traceable from intake to delivery.
- All tenant operations must enforce permission checks.

## 8) Workflow States (Draft)

### 8.1 Voucher Status
- `DRAFT` -> `CONFIRMED` -> `LOADING` -> `IN_TRANSIT` -> `PARTIALLY_DELIVERED` -> `DELIVERED` -> `CLOSED`

### 8.2 Trip Status
- `PLANNED` -> `LOADING` -> `DEPARTED` -> `AT_STOP` -> `COMPLETED` / `CANCELLED`

## 9) Non-Functional Requirements
- Responsive design for mobile/tablet/laptop/desktop.
- Desktop-first print layout and print authorization.
- Data isolation by tenant.
- Role-based authorization on every API/page action.
- Soft-delete for key entities to preserve history.
- Timezone-aware timestamps.
- Multilingual UI labels (Myanmar + English).
- Public page should be SEO-friendly (clean URL slug, metadata fields).
- Billing records must be auditable and immutable after finalization (except controlled adjustments).

## 10) Reporting (Phase 1 Recommended)
- Daily intake by warehouse.
- In-transit shipments.
- Delivery completion by destination.
- Freight payment outstanding report.
- Stock balance by warehouse and category.
- Subscription status report (active, overdue, suspended tenants).
- Monthly recurring revenue summary (platform-side).

## 11) Out of Scope (for v1 draft)
- Real-time GPS tracking.
- Advanced automated dunning (multi-step reminder automation).
- Public customer tracking portal.
- OCR/document scanning automation.

## 12) Assumptions and Open Points
- Assumes one platform owner account model exists.
- Exact permission catalog to be finalized during design.
- Accounting integration (if any) is future phase unless requested now.
